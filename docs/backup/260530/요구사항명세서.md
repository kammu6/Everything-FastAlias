## Everything FastAlias 요구사항 명세서

안티그래비티(Antigravity) IDE를 통한 바이브 코딩(Vibe Coding) 및 AI 에이전트 지시용으로 최적화된 구조화된 명세서입니다.

### 1. 프로젝트의 목적 및 개요

- **프로젝트명**: Everything FastAlias
- **목적**: 기존 `Everything.exe` 엔진의 강력한 로컬 파일 검색 기능에 사용자 정의 **'동의어/다국어/별칭(Alias) 매핑'** 기능을 더한 프라이빗 맞춤형 파일 탐색 인터페이스 앱 구축.
- **핵심 기능**:
- 사용자가 검색창에 특정 키워드(예: `사과`)를 입력하면, 매핑 테이블에 정의된 모든 연관어(예: `apple`, `🍎`)를 자동으로 결합하여 Everything 문법 형태로 치환 후 초고속 통합 조회.
- 외부 Excel 파일(`.xlsx`) 대량 업로드 및 앱 내 관리 UI를 통한 키워드 매핑 테이블 실시간 갱신 및 로컬 DB 영구 저장.

### 2. 기술 스택

- **런타임 및 데스크톱 쉘**: Electron (Node.js 20+ 기반)
- **프론트엔드 빌드 도구**: Vite
- **프론트엔드 UI**: React, TypeScript, Tailwind CSS v4, Lucide React (로컬 번들링 아이콘)
- **네이티브 DLL 바인딩**: `koffi` (C 기반 `everything64.dll` 연동용 고성능 FFI 라이브러리)
- **로컬 데이터베이스**: `better-sqlite3` (임베디드 SQLite3 데이터베이스)
- **Excel 파서**: `xlsx` (SheetJS)

### 3. 작업 폴더 및 파일 구조 추천안 (MVVM, One-Class Per File)

바이브 코딩 시 AI 에이전트가 코드를 명확히 분리하고 컨텍스트를 오독하지 않도록, **하나의 파일에는 하나의 클래스(또는 핵심 컴포넌트/함수)만 작성**하는 원칙과 **MVVM 패턴**을 엄격히 적용한 아키텍처입니다.

### 4. 기타 정보 (AI 에이전트 지시용 가이드라인)


#### 🛠️ 개발 시 에이전트(QueryTransformer)가 처리해야 할 핵심 로직 예제

안티그래비티 IDE에서 바이브 코딩을 진행하실 때, 백엔드의 `QueryTransformer.ts` 클래스에 다음과 같은 문자열 가공 흐름을 코딩하도록 지시하시면 됩니다.

1. **사용자 입력**: 사과 | banana

2. **입력어 분리**: 사용자가 입력한 검색어에서 연산자(`|` 등)를 기준으로 단어들을 쪼갭니다. (`사과`, `banana` 추출)

3. **매핑 단어 치환**: DB에서 각 단어의 동의어를 찾아서 `<원래단어|매핑단어>` 형태로 래핑합니다.

4. **재조합**: 쪼개졌던 연산자들과 결합하여 최종적으로 `<사과|apple> | <바나나|banana>` 문장으로 완성한 뒤 `everything64.dll`로 전송합니다.


#### 🤖 에이전트 필수 참조 및 구현 가이드**
>
> 1. **문서 및 리소스 참조**:
>    기능 구현 및 검색 쿼리 파싱 규칙을 설계할 때 아래 경로의 로컬 문서들을 반드시 사전 로드하여 문법 및 옵션을 준수하시오.
>
> - 도움말 옵션: `..\Everything검색기\docs\Everything Offical Manual\Everything.exe도움말.txt`
> - 검색 연산자 및 변경자 규칙: `..\Everything검색기\docs\Everything Offical Manual\Everything검색문법.txt`
> - 정규식 대응: `..\Everything검색기\docs\Everything Offical Manual\Everything정규식문법.txt`
> - 핵심 DLL 위치: `..\Everything검색기\docs\EverythingDLL\Everything64.dll`
>
> 2. **Everything DLL 바인딩 규칙**:
>
> - `backend/src/native/EverythingBridge.ts` 작성 시 `koffi`를 사용해 `Everything64.dll`을 로드할 것.
> - 한글 및 다국어 검색어 전달 시, 문자열 깨짐 방지를 위해 반드시 **`Everything_SetSearchW`** 및 **`Everything_QueryW`** 등 와이드 문자열 용 Win32 API를 사용하도록 래핑 클래스를 구성할 것.
> - 검색 결과 반환 시 UI 스레드가 블로킹되지 않도록 비동기 IPC 통신 혹은 Node.js 스레드 풀을 활용할 것.
>
> 3. **쿼리 트랜스포머 알고리즘**:
>
> - `QueryTransformer.ts`는 `better-sqlite3` 혹은 구동 시 캐싱된 메모리 `Map` 객체에서 동의어를 조회해야 함.
> - 사용자가 `사과` 입력 시, 검색어 문법 매뉴얼에 정의된 그룹화 `< >` 및 OR `|` 연산자를 참조하여 `<사과|apple|🍎>` 형태의 스트링으로 치환한 뒤 `EverythingBridge`로 전달할 것.

- 4. **Everything SDK 연동 주의점**:
  - `everything64.dll`과 통신할 때, 한글 경로를 다루거나 한글 검색어(`사과` 등)를 보낼 때는 반드시 **`W`가 붙은 와이드 문자열(UTF-16) API 함수**를 사용해야 윈도우 환경에서 글자가 깨지지 않습니다. (예: `Everything_SetSearchA` 대신 `Everything_SetSearchW` 사용)

  - Electron과 better-sqlite3의 네이티브 모듈 컴파일(Rebuild) 이슈better-sqlite3는 C++로 작성된 소스코드를 Node.js 환경에 맞게 컴파일해서 쓰는 '네이티브 애드온' 라이브러리입니다. 문제는 Electron이 사용하는 Node.js 버전과 PC 시스템의 Node.js 버전이 다를 때 "The module ... was compiled against a different Node.js version"이라는 에러를 뿜으며 앱이 켜지지 않을 수 있습니다.대비책: 프로젝트 설정 시 electron-rebuild 패키지를 설치하거나, 빌드 스크립트에 electron-builder install-app-deps 명령어를 포함하여 Electron 버전에 맞게 SQLite가 자동으로 재컴파일되도록 에이전트에게 지시해야 합니다.② 엑셀 대용량 업로드 시 UI 블로킹 및 DB 트랜잭션 처리사용자가 수천, 수만 개의 단어가 담긴 대형 엑셀 파일을 업로드하는 경우, SheetJS가 이를 파싱하고 better-sqlite3가 한 줄씩 DB에 넣으면 순간적으로 앱이 먹통이 될 수 있습니다.대비책: 엑셀 데이터를 DB에 밀어 넣을 때는 반드시 SQLite의 Transaction(db.transaction()) 기능을 사용하도록 하세요. 한 건씩 대입하면 10초 걸릴 작업이 트랜잭션으로 묶으면 0.1초 만에 끝납니다.③ Everything 대소문자 및 경로 검색 기본값 제어제공해주신 문서에 명시된 대로 Everything은 -case(대소문자 구분), -matchpath(전체 경로 검색) 등의 수많은 조건 변경자를 가지고 있습니다. 대비책: 스마트 매핑으로 단어가 <사과|apple>로 치환되어 전달될 때, 기본적으로 대소문자를 구분하지 않을 것인지(nocase), 혹은 파일명만 매칭할 것인지(nomatchpath)에 대한 기본 가공 규칙 및 옵션 초기화 함수(Everything_SetMatchCase, Everything_SetMatchPath)를 DLL 로드 직후 명시적으로 세팅해 주어야 의도치 않은 검색 결과가 나오는 것을 방지할 수 있습니다.

- 5. 문법은 완벽히 호환되지만, 프로그램(`Everything.exe`)과 라이브러리(`everything64.dll`)의 인터페이스 차이 때문에 딱 하나 코딩으로 챙겨야 할 부분이 있습니다. `Everything.exe` 프로그램에서는 상단 메뉴나 옵션 창을 통해 대소문자 구분, 정규식 사용 여부 등을 마우스 클릭으로 켜고 끌 수 있습니다. 하지만 DLL은 눈이 없는 라이브러리이므로, 검색 문자열을 보내기 전에 **현재 검색 조건이 무엇인지 코드로 명시**해 주어야 합니다.

예를 들어, 정규식 문법을 사용하고 싶다면 문자열을 보내기 전에 아래와 같이 DLL 함수를 먼저 호출해 주는 식입니다.

```typescript
// 에이전트가 코딩해야 할 백엔드(EverythingBridge.ts) 예시
import koffi from "koffi";

// 1. DLL 함수 정의 (koffi 방식)
const Everything_SetSearchW = everythingLib.func(
  "void Everything_SetSearchW(const wchar_t *)",
);
const Everything_SetRegex = everythingLib.func("void Everything_SetRegex(int)");
const Everything_QueryW = everythingLib.func("int Everything_QueryW(int)");

// 2. 검색 실행 로직
function executeSearch(processedQuery: string, useRegex: boolean) {
  // 정규식 활성화 여부를 DLL에 먼저 전달 (true면 1, false면 0)
  Everything_SetRegex(useRegex ? 1 : 0);

  // 가공된 문법 문자열 전달 (예: "<사과|apple> | <바나나|banana>")
  Everything_SetSearchW(processedQuery);

  // 검색 실행 명령
  Everything_QueryW(1);
}
```

**[Everything FastAlias 백엔드 개발 지침 가이드]**

1. DLL 경로 바인딩 분기 처리
- native/EverythingSdk.ts 클래스는 개발 단계(process.env.NODE_ENV)일 경우 
  "../../assets/dll/Everything64.dll" 경로를 로드하고, 
  app.isPackaged가 true인 배포 상태일 때는 process.resourcesPath 기준 
  "resources/Everything64.dll"에서 파일을 찾도록 동적 경로 로직을 반드시 구현하라.

2. UTF-16 와이드 캐릭터 통신 준수
- 한글 및 다국어 검색어 전달 시 글자 깨짐 현상을 근본적으로 차단하기 위해, 
  koffi 바인딩 함수 선언 시 char* 계열의 'A' 함수(Everything_SetSearchA) 사용을 엄격히 금지한다.
  반드시 'wchar_t*' 규격으로 맵핑되는 'W' 함수(Everything_SetSearchW, Everything_GetResultPathW)를 사용하도록 선언하라.

3. QueryTransformer 문법 변환 규칙 참조
- service/QueryTransformer.ts 작성 시, 에이전트는 반드시 'docs/Everything Offical Manual/' 폴더 내부의 
  'Everything검색문법.txt'와 'Everything정규식문법.txt'를 최우선 순위로 읽고 규칙을 파악해야 한다.
- 예외 검색 옵션 구현 시, 사용자가 지정한 '제외 단어'가 있다면 '!' 기호로 묶어주고,
  미디어 필터 선택 시 상용구 패턴(video:, audio:, pic:, doc:)을 쿼리 끝에 조합해야 한다.
- 검색어 그룹화는 중괄호 {}가 아닌 부등호 기호 < >를 명확히 사용하여 처리되도록 설계하라.

4. SQLite 재컴파일 에러 대비
- better-sqlite3가 Electron의 내부 V8 엔진 버전에 맞게 바인딩되도록, 
  패키지 설치 및 빌드 스크립트 실행 시 'electron-rebuild' 파이프라인이 작동할 수 있는 
  package.json 종속성 구성안을 선제적으로 보장하라.

## 🛠️ 단축키를 고려한 상수 파일 설계 예시

### 1. 백엔드 영역 (`backend/src/config/AppConstants.ts`)

Electron은 OS 전역에서 작동하는 글로벌 단축키(Global Shortcut)를 등록할 수 있습니다. 이를 메인 프로세스 상수 파일에서 관리합니다.

```typescript
export const APP_CONSTANTS = {
    // 1. IPC 통신 채널 이름 (프론트-백엔드 간의 오타 방지용)
    IPC_CHANNELS: {
        SEARCH_REQUEST: 'search:request',
        SEARCH_RESULT: 'search:result',
        OPEN_ALIAS_MANAGER: 'window:open-alias',
    },

    // 2. Everything DLL 기본 설정값
    DLL_CONFIG: {
        DEFAULT_MAX_RESULTS: 1000,
        RECYCLE_BIN_PATH: '!$Recycle.Bin',
    },

    // 3. 추후 도입할 글로벌 단축키 (앱이 백그라운드에 있어도 작동)
    GLOBAL_SHORTCUTS: {
        SHOW_MAIN_WINDOW: 'CommandOrControl+Alt+F', // 앱 숨기기/보이기 토글 hotkey
    }
} as const; // 읽기 전용 강제

```

### 2. 프론트엔드 영역 (`frontend/src/config/UiConstants.ts`)

React 내부에서만 쓰이는 화면 제어용 단축키(예: `Esc`를 누르면 검색창 초기화, `방향키`로 결과 테이블 이동 등)와 UI 고정 수치들을 관리합니다.

## 💡 추후 단축키 구현 시 꼭 알아두어야 할 꿀팁

바이브 코딩 시 에이전트에게 단축키 구현을 요청할 때, 단축키의 **성격**에 따라 구현 기법이 완전히 달라지므로 아래 개념을 명시해 주어야 삽질을 안 합니다.

1. **글로벌 단축키 (App-Wide / Global)**
* **구현**: 반드시 백엔드(`backend/src/main.ts`)에서 Electron의 `globalShortcut` 모듈을 사용해 OS에 등록해야 합니다.


2. **로컬 단축키 (Window-Focused / Local)**
* **개념**: 앱 창이 켜져 있고, 사용자가 우리 앱을 클릭해둔 상태에서만 작동하는 단축키입니다. (예: 결과 목록에서 `Enter`를 치면 파일 실행)
* **구현**: 프론트엔드(`frontend/src/viewmodels/LayoutViewModel.ts`)에서 글로벌 `window.addEventListener('keydown', ...)` 이벤트를 걸어서 UI 상수를 기반으로 분기 처리하는 것이 가장 정석입니다.
